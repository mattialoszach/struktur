# Verification status

Updated 19 September 2026. This records local evidence, not App Store approval or a guarantee of defect-free operation.

## Automated checks

- 127 tests pass with zero failures.
- Full-window Notes follow-up (19 September): profiling the running app exposed substantial SwiftUI control construction/layout around the editor. The previous edit-only tests missed this work. The title now uses a native field with fixed height; title and body typing send no workspace-wide notifications. The saving indicator observes its own small status object, and pending library/word-count updates publish once after the idle delay. Header and toolbar state are separated; a single wrapping layout replaces two copies of the toolbar, menus, and popovers built by `ViewThatFits`. Sidebar navigation no longer animates the entire page.
- Saving an unchanged workspace now skips both JSON writes and publication of an unchanged error. This prevents multiple disappearing dashboard/note views from repeatedly saving and invalidating navigation. Added regressions verify zero writes/notifications for clean flushes, immediate title export with coalesced refresh, nonoverlapping toolbar wrapping, and native title/body input in a complete `RootView` window. Existing save failure, ordered flush/import, migration, and recovery tests remain in place.
- Notes typing/redraw follow-up (19 September): Write now uses native TextKit 2 with a stable 14-point font and line spacing. Markdown parsing and document typography run in Preview. Ordinary unannotated keystrokes do not rewrite text attributes; annotated edits style only the inserted range inside a native content-editing transaction and request redraw immediately. A regression catches the previous highlighted-text bug where the source changed without repainting. A second regression reproduces a delayed SwiftUI snapshot overwriting new text and clearing undo; editor updates now fetch the current document before synchronizing.
- Performance evidence: the SwiftUI-hosted Notes page benchmark includes native key handling and forced display for short notes and a single approximately 30,000-character paragraph. The original long-paragraph path measured approximately 122 ms p95 per edit; the latest suite measured approximately 27 ms (short-note p95: approximately 6 ms). The separate 5,000-paragraph Unicode/highlight edit-and-store benchmark measured approximately 0.18 seconds for 100 insertions (about 1.9 ms p95, with no workspace notifications during typing). The new complete-window fixture measured approximately 203 ms for initial layout; its title/body edit samples, including a 10 ms run-loop wait and layout/display, measured approximately 73/29 ms p95. These are local debug-build diagnostics, not physical key-to-display latency guarantees. The earlier edit-only benchmark did not establish visible responsiveness; real window captures during typing supplement it in the native checks below.
- Background persistence: autosave encodes immutable workspace snapshots and writes atomically on a serial utility queue. Word counting also runs off the UI thread. Five dedicated regressions cover a deliberately blocked encoder while new typing continues, stale save completions, explicit-save/import ordering, failure/retry, one-time migration backups, unreadable-file protection, and clean-save deduplication. Explicit navigation/quit flushes of unsaved changes and import backups wait for that queue and can still take time for large workspaces. Reference guidance: Apple's [app responsiveness](https://developer.apple.com/documentation/xcode/improving-app-responsiveness) and [SwiftUI performance](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance).
